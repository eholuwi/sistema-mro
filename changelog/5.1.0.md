🎯 Resumo Executivo
Segunda fase (F2) da evolução v5.x (ver `docs/PLANO_V5_EVOLUCAO.md`). A **API do SCM** (só-leitura,
anônima, interna) passa a ser **fonte primária persistindo no `mro.db`**: um clique em **"Atualizar
agora"** puxa as SCs dos solicitantes MRO (cabeçalho via `ByUser` + itens via `Timeline`) e grava no
banco — status, datas, centro de custo, itens e preços. O **Relatório de SCs (Excel)** continua
valendo como **fallback/complemento**; a API **nunca** é dependência exclusiva. Elimina o trabalho
manual diário de upload.

🔌 Cliente da API (`services/scm_client.py`)
- **NOVO** `sc_por_usuario(usuario, ini, fim)` → `GET /solicitacaoCompras/ByUser/{u}/{ini}/{fim}`
  (datas `yyyyMMdd`). **Sem cache** (é a fonte do sync — precisa de dado fresco). Endpoint FILTRADO.
- **NOVO** `usuarios()` → `GET /Usuario` (diretório; cache 1 h) — resolve o código Protheus do
  solicitante pelo nome.
- Itens vêm do já existente `sc_timeline(sc_id)` (reuso).

🔄 Sincronização (`services/scm_sync.py` — NOVO)
- **Parsers puros** `normalizar_sc_api` / `normalizar_itens_api` — trim do padding Protheus, datas
  nulas `0001-01-01`→None, campo de preço com o typo **`valorUnitaro`**→`preco_unitario`. Testáveis
  com fixtures reais (`tests/fixtures/scm/`).
- **Orquestrador** `sincronizar(periodo_dias=180, progress_cb)` — por solicitante MRO com código:
  `ByUser(hoje−180, hoje)` + `Timeline` por SC → upsert numa **transação por solicitante** (queda no
  meio preserva os concluídos); backup `_backup_db('sync-api')` 1×/dia; log em `log_importacoes`
  tipo **`api_scm`**. Rede (Timeline) roda **fora** da transação de escrita.
- **Dedup vs Excel** (mesma SC): padrão COALESCE de `ingerir_scm` — a API atualiza status/datas/centro
  de custo; campos só-Excel (PO, fornecedor, comprador, saving, previsão NFe) ficam **intactos**.
  **Nunca rebaixa** (garante "re-sync não regride"): rank de status (Aguardando<Cotação<Pedido<
  Recebido<Cancelado) — status do banco mais adiante que o da API é mantido. Divergências acumuladas
  em `detalhe_json` (cap ~50).
- Status: mapeia o **código** da API (`01/03/05/…`) para os rótulos do MRO **reusando**
  `_status_sc_importado` (mesmo vocabulário do Excel). ⚠️ Códigos §7.13 da doc SCM são **inferidos** —
  o código cru fica salvo em `status_protheus`; validar/ajustar com dado real.
- Resolução de código: `resolver_codigos_solicitantes()` casa o nome do solicitante com `/Usuario`
  (normaliza os dois lados). `ultima_sync()` expõe a última sincronização.

📦 Itens fora do inventário (fecha um buraco antigo)
- Antes, item de SC com PN **fora do inventário MRO** era **descartado** na ingestão. Agora a SC é
  criada e o item vai para a **nova tabela `itens_sc_externos`** (visibilidade do ciclo SC→PO; backlog:
  "promover para o inventário"). Vale para **Excel** (`ingerir_scm`, `origem='excel'`) e **API**
  (`origem='api_scm'`), via o helper único `_upsert_item_sc_externo` (sem duplicar SQL).

🗄️ Banco de Dados (migração ADITIVA, com backup automático)
- `solicitacoes_compra` += `sc_id_scm` (INTEGER), `centro_custo` (TEXT), `data_sync_api` (TEXT).
- `itens_sc` += `origem` (TEXT).  ·  `solicitantes_mro` += `codigo` (TEXT).
- **NOVA** `itens_sc_externos` (sc_id FK CASCADE, part_number, descrição, qtd, unidade, preço, valor,
  numero_po, data_necessidade, origem, `UNIQUE(sc_id, part_number)`).
- Índices `idx_sc_solicitante`, `idx_sc_comprador`, `idx_sc_scmid`, `idx_isc_ext_sc`.
- Só ADD COLUMN/CREATE IF NOT EXISTS (idempotente). Código antigo roda sobre o schema novo.
